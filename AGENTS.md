# Правила работы с проектом ПУСК

Перед изменениями прочитайте [архитектурное решение](docs/prototype-architecture.md).
Это единый источник договорённостей о версиях. Не заменяйте его предположениями
из названий папок или предыдущих задач.

## Обязательные правила

1. Архитектура: независимые копии приложений под общей демонстрационной оболочкой.
   Не превращать их в одно приложение с условными ветками X1/X2/X3.
2. `prototype/` — зафиксированный исходный прототип X1. Не редактировать,
   не перемещать, не переименовывать его файлы и не менять существующие пути
   в рамках задач по оболочке или экспериментам. Даже исправление ошибки
   исходника делать в отдельной копии. Прямое указание пользователя изменить
   сам исходник имеет приоритет; такое изменение требует обновления документации.
3. Новые варианты размещать в `variants/<id>/`, оболочку — в `demo/`.
   `variants/current-mobile/` — рабочая копия текущей системы для видеосверки,
   не UX-эксперимент. Перед работой с ней прочитайте её README с границами точности.
   `demo/index.html` переключает независимые iframe; перенос состояния отсутствует.
   `variants/product-proposal/` — X2 по предложению из презентации для продакта.
   `variants/visit-workspace/` — X3 для удобного внесения блоками. Его локальный
   черновик хранится только под ключом `pusk:visit-workspace:v1`; сброс не должен
   удалять другие ключи. Цели X2 и X3 не смешивать.
4. У каждого варианта собственные HTML, CSS, JavaScript и изменяемые ресурсы.
   Не подключать код или стили другого варианта либо исходника по живой ссылке.
   Общие изменяемые зависимости, связывающие поведение вариантов, не вводить.
5. Если появляется сохранение данных, разделять его по стабильному ID варианта.
   Ответы, черновики и сброс одного варианта не должны менять другой.
6. `v2/`, `v3/`, `frames/`, `hi/`, `sample/`, `scenes/` — материалы проекта;
   не считать их работающими версиями приложения и не занимать их под новые версии.
7. Для каждой новой копии создавать `README.md`: ID, название, точный источник
   копирования, дата, цель, изменения, доступные сценарии и ограничения.
   Номер X3 не означает, что его надо автоматически копировать из X2.
8. Сборку выбранных решений делать отдельным вариантом. Не перезаписывать
   исходник и ранее показанные варианты ради «финальной версии».
9. Отличать принятое решение от реализованной функциональности. Не заявлять,
   что оболочка, перенос состояния или автоматическое смешивание решений уже есть.
10. Новые архитектурные договорённости фиксировать в `docs/prototype-architecture.md`.
    Не дописывать за пользователя ответы на открытые вопросы.

## Проверка изменений

- Перед работой и после неё сверить SHA-256 исходника с
  `docs/baseline-sha256.json`. При несовпадении выяснить причину; не восстанавливать
  файлы и не обновлять контрольные суммы автоматически.
- При реализации проверить запуск исходника по прежнему пути, запуск затронутой
  копии, её сценарий и отсутствие влияния на соседние варианты.
- Документационные изменения не требуют запуска приложения. Контрольные суммы
  подтверждают неизменность файлов, но не заменяют функциональную проверку.

Документация и контрольные суммы сами по себе не являются блокировкой записи
или резервной копией. При появлении Git сохранять исходное состояние в истории;
не считать, что Git уже настроен.


X4: variants/question-pager — один вопрос на экран и оглавление.
Оболочка demo/shell.js выводит варианты внизу бургер-меню, без верхней DEV-панели.
Её runtime-стили и управление меню не должны затрагивать ответы и логику копий.
Собственное хранилище pusk:question-pager:v1. Не менять X3 ради X4.
Семь групп — только тестовый сценарий; не добавлять вымышленные вопросы в аудит.
