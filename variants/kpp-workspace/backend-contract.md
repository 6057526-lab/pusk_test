# X4: контракт рабочего пространства

13.10.2026. Реализован локальный repository; боевой backend не подключён.

Внешняя граница: createRepository({readState, writeState, actor, now}) возвращает
Promise-интерфейс load(), query(kind, filter), execute(command).
Фронт сохраняет старые visits и новое workspace одним состоянием в собственном
ключе. Сетевому адаптеру понадобится реализация этих операций и серверная проверка
всех переходов/прав, а не копирование localStorage в API.

## Команды

Обязательны id, type, entityId, expectedRevision, payload.
id защищает от повторного выполнения; revision — от устаревшего решения.
Ошибка сохранения отклоняет Promise; UI не принимает изменённые сущности.

| Команда | Объект | Проверяемый переход |
| --- | --- | --- |
| approve_plan | plan | текущая submitted-версия → approved, задача согласования completed |
| return_plan | plan | submitted → returned, задача ждёт директора; пояснение по демо-правилу |
| link_assignment | assignment | одно назначение → один черновик; payload содержит visitId/visit |
| complete_assignment | assignment | open → completed; задача ознакомления создаётся отдельно |
| complete_local_visit | local visit | создаёт задачу ознакомления для свободного аудита |
| acknowledge | task | открытое ознакомление → completed |
| demo_resubmit | plan | новая версия от директора; старые версии сохранены |
| demo_report | action | сообщение исполнителя, ещё не подтверждённое устранение |
| demo_verify / demo_rework | action | отдельный проверяющий примера; производственная роль не установлена |

Команды demo_* — средства демонстрации передачи работы. Боевой адаптер не
должен принимать их от КпП как его производственные права.

## Чтение

query('queue', {siteId,status,query}), query('plan',{id}),
query('program',{siteId}) и коллекции workspace возвращают данные примера.
Период аналитики использует дату визита; задачи/ПД сохраняют собственные даты.
Назначенный визит содержит assignmentId, questionIds, scopeLabel.
Частичный состав применяется к прогрессу, проверке, проценту и PDF.

## Что сервер должен определить

- Аутентификация, фактический портфель, объектные права, делегирование/смена ролей.
- Состояния задач/ПД/действий и подтверждающий исполнение; исторические версии.
- Производственная формула, цикл, зачёт, правила по типам визитов.
- Генерация назначений, состав повторных, сроки и стадии ИПУР.
- Файлы/фотографии, ограничения, журнал, конкурентные решения и уведомления.
- Загрузка, отсутствие доступа, сохранение и восстановление при сбое сети.

Отдельные полные опросники других типов не переданы. Поддерживающий/контрольный
этап демонстрируется существующим пищевым аудитом с явной оговоркой. Такое
назначение нельзя автоматически перенести в действующую программу ПУСК.


## Передачи и структура ПД — дополнение 14.10.2026

workspace дополнен people, planTasks, planDrafts, referenceVisits;
site.kppId, task/assignment.assigneeId, visit.creatorId и sourceInitiatorId
разделяют текущего исполнителя и исторического автора.
planVersion.tasks/groupMap — снимок группировки; старые items не переписываются.
Архивные действия доступны для чтения, в текущую сводку не входят.

Новые локальные demo-команды: save_plan_draft, submit_plan_draft,
restore_regulation, transfer_kpp, view_as (в коде с префиксом demo_).
Все используют прежние command.id/expectedRevision и сериализованную запись.
Они не являются серверными правами пользователя КпП.
Демо-черновик директора не изменяет submitted/approved версию до отправки.
При изменении состава версия фиксирует новые задачи/действия; статусы исполнения
сохраняются только у неизменённых действий, новые имеют открытый статус примера.
demo_report принимает evidence[{name,url}] с локальным PNG/JPEG до 3 МБ.
Рабочий backend должен хранить файлы отдельно и проверять объектные права/содержимое.

Текущий демо-участник хранится в settings.currentKppId. Ограничения фронта
и смена этого поля не являются безопасной серверной аутентификацией.
Доступ прежнего сотрудника к истории, роль проверяющего, перезапуск заблокированного
процесса, правила новых опросников/циклов не восстановлены и требуют отдельного контракта.

## Каталог и подготовка визита — 14.10.2026

checklist-catalog.js содержит локальные UI ID и наименования примера, ready и
questionCount только для переданного пищевого опросника. В backend нужны
опубликованные checklistId/versionId, группа прохождения, область ПБО, правила
доступности и фактические вопросы/ответы каждого чек-листа; свободная смена ID
не может менять уже начатую версию. Назначения должны передавать точную версию
и questionIds, а не брать текущий выбор формы создания.

Локальный selected checklistId хранится в корневом состоянии X4, новые пищевые
visits имеют checklistId=food-safety. Отсутствие поля у прежних записей означает
старый пищевой аудит; неизвестный ID не должен открываться с его вопросами.
Подбор черновика: ПБО + дата + чек-лист, исключая assignmentId и done.
visitPreparations[{id,pbo,date,checklistId,creatorId}] — сохранённые реквизиты
неподключённого опросника; это не visits и не выполненные programItems.
Записи не содержат ответов и не участвуют в метриках визитов/согласовании/ИПУР.
Их сохранение не публикует назначение. Для бизнес-планирования нужна дата
открытия ПБО; фронт её не вычисляет и не утверждает готовность к запуску.

## Два демонстрационных состава после встречи — 14.10.2026

Основной каталог показывает food-safety (48) и people-practices (5 демо).
people-questions.js копирует тексты и допустимые ответы пяти вопросов переданного
прототипа; локальные p_q1..p_q5 не являются ID опубликованной производственной версии.
Фальсификация — условное поле только people-practices, требуется перед завершением.
Legacy food значения сохраняются в данных, но не участвуют в итоге и не выводятся.

Для backend нужны неизменяемые checklistVersionId и точный набор вопросов,
полный опросник практики, реальные закрепления ПБО и состояние IPUR, правила
доступности типов/дат/назначений, сохранение черновика и серверная блокировка
после завершения. Красное предупреждение ниже 80% сейчас основано на доле «Да»
от всех вопросов после заполнения некритических; это не утверждённые веса.
Итоговый статус пока остаётся демонстрационным правилом критического «Нет» /
фальсификации «Да» в практике. Пищевые сравнения не смешивают другие checklistId.
visitSetup и answerMode — локальные предпочтения интерфейса, не серверные права.

## Демонстрационное фото и просмотр разделов — 14.10.2026

visits[].demoPhotos[questionId]=true — исключительно отметка UI демо, не файл,
не URL и не подтверждение устранения. Реальные сохранённые photos не заменяются.
PDF выводит явную подпись о демонстрации. Для рабочего backend эту механику
следует заменить настоящим вложением и серверной проверкой прав/содержимого.
Автоматический переход запускается только при «Да». Исходные причины «Нет»
и свободный комментарий сохраняют прежний формат.

## Уточнение порога и блокировка незаполненной проверки — 14.10.2026

По явному ответу пользователя правило X4 обновлено: complete && percent < 80
— неудовлетворительно; ровно 80% и выше допустимы. Критический «Нет» и факт
фальсификации в практике имеют прежний приоритет. Это заменяет прошлое
описание порога как одного предупреждения; доля «Да» и отсутствие весов сохранены.
«Неактуально» — заполненный допустимый ответ без вклада в числитель «Да».
Рабочая производственная формула/веса и исключения знаменателя не импортированы.
Валидация проверки требует ответов на все questionIds своего состава, включая
частичный. Пропуски оставляют интерфейс на форме. Финальная серверная проверка
и версионирование правил остаются задачей рабочего backend.

## Причина при ответе «Нет» — 14.10.2026

Пользователь подтвердил обязательность причины перед проверкой.
comments[questionId] — единое поле комментария и свободной причины; reasons[questionId]
— массив выбранных исходных why. При отсутствии why и для «Другое» комментарий
обязателен. Фотография необязательна. Валидация ограничивается
questionIds назначенного состава. Backend должен повторить проверку допустимых
вариантов/непустого текста и финальной неизменности. Старые reasonTexts сохраняются
как совместимые данные и однократно объединяются с comments без потери обоих
текстов; commentReasonMigration=1 предотвращает повтор при перезапуске.
Реальные завершённые записи требуют версионирования правил,
фронтенд не заставляет переписывать завершённые демонстрационные визиты.

История завершённых визитов удалена из текущей навигации X4. Сохранённые записи
не удаляются. В очереди задач показываются только незавершённые визиты и реальные
локальные задачи ознакомления со статусом open, а не список всех завершений.
Просмотр итогов разделов не редактирует ответы; до завершения доступен общий
возврат в анкету. После подтверждения ответы неизменяемы.

## Лента задач текущего демо — 14.10.2026

taskFilter=all/checklists/results — локальный фильтр представления, не статус задачи.
sourceTaskId/sourceTaskAuthor/sourceTaskCreated у визита сохраняют происхождение
входящего примера X1 и устраняют дубли при продолжении. Это не идентификаторы
производственных задач. Входящие примеры сейчас статичны, настоящая доставка,
пагинация, автор/время создания и права должны поступать от backend.
Без исходного времени карточка показывает дату визита с соответствующей подписью,
а не выдаёт её за время создания. Отдельный список результатов берёт только
acknowledge со статусом open по закреплённым ПБО и получателю currentKppId.
Для прежних записей без assigneeId сохраняется совместимость по закреплению ПБО.
Команда acknowledge использует существующую проверку владельца и ревизии.
Неизвестные опросники не создают фиктивных пищевых визитов. Назначения/планы
расширенного примера остаются в модели, но не выдаются за исходные задачи X1.
