# ПУСК: независимые прототипы под общей оболочкой

Дата решения: 23 сентября 2026 года.

Статус: пользователь одобрил подход независимых копий под общей оболочкой.
23 сентября создана подготовительная копия `variants/current-mobile/` для
видеосверки текущей системы и минимальная оболочка `demo/index.html`.
Точность и ограничения копии описаны в её README. Создан X2
`variants/product-proposal/` по презентации для продакта. X3 `variants/visit-workspace/` реализует внесение блоками и локальный черновик.

## Цель

Сохранить исходный кликабельный ПУСК, экспериментировать с интерфейсами и
пользовательскими путями в команде и показывать заказчику несколько решений
одной задачи. После обсуждения собрать выбранные элементы в отдельный вариант.

Успешный результат: на одном демонстрационном экране можно выбрать X1, X2,
X3 и последующие варианты, пройти сценарий в каждом и вернуться к неизменному
исходнику. Новую копию можно добавить без переписывания предыдущих.

## Текущее состояние — проверенные факты

- Рабочие файлы прототипа: `prototype/index.html`, `prototype/css/styles.css`,
  `prototype/js/app.js`.
- Это приложение на HTML, CSS и JavaScript. Экраны переключаются внутри
  приложения; в JavaScript есть состояние текущего экрана и заполнения аудита.
- Общая оболочка `demo/index.html` переключает исходник, подготовительную копию, X2, X3 и X4.
- Каталоги `v2/` и `v3/` содержат изображения, а не приложения X2 и X3.
- Рядом находятся материалы `frames/`, `hi/`, `sample/`, `scenes/` и исходный MP4.
- На дату решения каталог проекта не является Git-репозиторием.
- Исходный прототип не закончен. Его фиксация не означает, что все сценарии
  реализованы или проверены.

## Принятая модель

**X1 — фиксированная база.** Существующий `prototype/` сохраняет файлы,
внешний вид, имеющиеся переходы и прямой путь запуска. Контрольные суммы
его трёх файлов записаны в `baseline-sha256.json` рядом с этим документом.

**X2, X3 и далее — независимые альтернативы.** Вариант может происходить
от исходника или от другой явно выбранной копии. Номер — обозначение в
демонстрации, а не оценка качества и не обязательная последовательность развития.
Каждая копия содержит собственный код и может менять не только оформление,
но и порядок шагов, формы и навигацию.

**Доработка базы — отдельная рабочая копия.** Незавершённость исходного
прототипа не разрешает менять зафиксированный X1. Дальнейшее воспроизведение
текущей системы ведётся отдельно. Новую базу для будущих экспериментов фиксируют
явным решением, сохраняя старую базу и уже показанные варианты.

**Итог — отдельная сборка решений.** Например, навигация из X2 и форма из X3.
Перенос и согласование этих элементов — самостоятельная работа с проверкой
целого сценария. Автоматический конструктор произвольных сочетаний не обещан.

Стабильный ID копии не меняется при переименовании её пользовательского заголовка.

## Оболочка и изоляция

Оболочка отвечает за выбор и описание вариантов, приложение внутри — за свой
интерфейс и сценарии. По запросу пользователя от 23 сентября верхняя панель
DEV удалена. Переключатель находится внизу бургер-меню: «Варианты прототипа».
Оболочка `demo/shell.js` добавляет только меню управления и полноэкранные стили
в DOM загруженного same-origin iframe. Файлы исходника и соседних копий
при этом не меняются, ответы и бизнес-логика не читаются и не переносятся.
На внутренних экранах оболочка добавляет кнопку доступа к тому же меню.
Прямой запуск каждой копии сохраняет её собственный вид без элементов оболочки.
Этот способ рассчитан на размещение всех статических файлов на одном origin.

Для изоляции DOM, CSS и JavaScript используются отдельные iframe. При переключении
скрытый iframe сохраняет свой сеанс. Кнопка «Начать заново» перезагружает только
выбранную копию; для X3/X4 после подтверждения удаляется только их собственный
ключ черновика. Простое подключение стилей и скриптов всех копий в один документ
не обеспечивает требуемую независимость.

Если используется localStorage или другое хранилище, данные разделяются по ID
варианта. Сам по себе iframe на одном origin не разделяет localStorage.
Сброс одного варианта не должен очищать данные остальных.

Оболочка не должна требовать изменения файлов исходника. Новые прототипы
не зависят от его изменяемого кода по ссылке. Ресурсы, которые предполагается
редактировать в эксперименте, копируются в этот эксперимент.

## Правила добавления варианта

1. Определить цель эксперимента и исходную копию. Если источник не следует
   из задачи, уточнить его, не выбирать автоматически последний номер.
2. Создать самостоятельную копию в `variants/<stable-id>/`.
3. В её README записать ID, название, дату и источник копирования с привязкой
   к состоянию файлов: Git commit при наличии Git либо контрольные суммы.
4. Описать изменения, поддерживаемые сценарии и известные ограничения.
5. Когда оболочка будет реализована, зарегистрировать вариант в её списке
   установленным при реализации способом.
6. Проверить изменённый сценарий и изоляцию, сверить контрольные суммы исходника.

Показанный заказчику вариант сохранять как воспроизводимый снимок;
последующие изменения делать в новой копии, если задача явно не предусматривает
редактирование существующего варианта.

## Открытые вопросы — не считать согласованными

- Для подготовительной видеосверки используется сохранение собственного сеанса
  каждой копии при переключении. Это технический выбор первого стенда.
  Требуется ли в будущем переносить шаг и данные между UX-вариантами, ещё не решено.
- Если потребуется перенос состояния, как сопоставлять шаги разных сценариев
  и обрабатывать отсутствующий в другой версии шаг? Единого соответствия пока нет.
- Как запускать и публиковать демонстрацию для команды и заказчика?
  Хостинг и способ совместной разработки ещё не выбраны.

Эти вопросы не препятствуют фиксации архитектуры, но соответствующее поведение
нельзя объявлять реализованным или обещать без отдельного решения.

## Критерии проверки будущей реализации

- Исходный прототип доступен по прежнему пути, его файлы совпадают с фиксацией.
- Выбор варианта показывает правильное приложение и его название.
- Изменения оформления, логики и данных одной копии не затрагивают другие.
- Варианты позволяют пройти заявленные в их README сценарии.
- Добавление копии не требует переделки исходника или соседних приложений.
- Переключение и сброс соответствуют отдельно принятому решению о состоянии.

## Изменение договорённостей

Этот документ — основной источник решения; `AGENTS.md` содержит его краткие
обязательные правила. При изменении архитектуры обновлять оба документа
согласованно и записывать дату, причину и основание изменения здесь.
Смена требований пользователем имеет приоритет над ранее принятым решением.
Контрольные суммы не обновлять просто ради устранения обнаруженного расхождения.
