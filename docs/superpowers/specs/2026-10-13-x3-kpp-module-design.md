# X3: рабочее пространство КпП

Дата: 13.10.2026. Основание: пользователь одобрил исследование
`docs/kpp-product-audit-2026-10-13.md` и поручил расширить существующий X3 до
целого пути КпП. Этот документ конкретизирует реализацию для review.

## Цель и границы

КпП видит свой портфель нескольких ПБО, понимает ожидаемое действие,
согласует или возвращает план директора, проводит назначенные проверки,
продолжает черновики и разбирает результаты/историю. Бизнес может пройти эти
сценарии в самостоятельном фронтенд-прототипе.

Работа ведётся только в `variants/enterprise-audit/` с прежним стабильным ID
и хранилищем `pusk:enterprise-audit:v1`. X1, X2 и архивные копии не меняются.
Существующие ответы сохраняются. Демонстрация не получает реальные права ELMA,
серверное сохранение, многопользовательское согласование или полноценный офлайн.
Подключение сервера будет самостоятельной работой: доступы, назначения,
конкурентные изменения, файлы, вычисления и аудит операций требуют реализации.

## Информационная архитектура

Основная мобильная навигация: **Главная · Предприятия · Задачи**.
Планы, визиты, программа и аналитика доступны из предприятий и общего меню.
На desktop рабочая очередь и портфель могут располагаться рядом.
Текущий зелёный стиль, типографика, панели выбора и иконки X3 сохраняются;
неудовлетворительный результат получает отдельное предупреждающее оформление.

| Экран | Что видно | Главное действие |
| --- | --- | --- |
| Главная | Очередь решений/назначений/черновиков; краткая сводка портфеля | Открыть конкретную работу |
| Предприятия | Закреплённый демонстрационный портфель, поиск и фильтры | Открыть ПБО |
| Предприятие | Ожидаемые действия, ПД, назначенные визиты, история и последние основания | Перейти к задаче или плану |
| Задачи | Тип, ПБО, срок, состояние, основание, исполнитель | Открыть доступную задачу |
| Задача | Зачем назначена, сроки, исходные документы, следующее действие | Согласовать ПД / открыть проверку / ознакомиться |
| Планы действий | ПБО, версия, согласование, актуальность, состояние исполнения | Открыть план |
| План | Автор-директор, версия, задачи/действия, сроки, история, документ | Согласовать или вернуть на доработку |
| Действие | Исполнитель, срок, состояние, пояснение/доказательство, связь с основанием | Просмотреть; права подтверждения отдельно |
| Программа | Назначенные обязательства примера, выполненные/ожидающие, исходные сроки | Открыть назначенную проверку |
| Повторные / ИПУР | Назначение, направление, стадия, состав проверки и история | Открыть следующий доступный этап |
| Аудит | Существующие вопросы, причины, комментарии, фото, сохранение | Проверить и завершить |
| Проверка / результат / документы | Все ответы и все основания результата, предварительный и окончательный PDF | Исправить до подтверждения / ознакомиться после |
| Аналитика | Сопоставимые результаты, разделы, замечания, история одного ПБО | Перейти к записи и связанной работе |

## Рабочие сценарии

1. Главная → ПД на согласовании → версия и действия → согласовать → решение
   в истории, закрытая задача согласования, план доступен для просмотра.
2. Та же точка → возврат с объяснением → ожидание директора → новая версия →
   повторное согласование. Старые версии/решения сохраняются.
3. Предприятие → актуальность плана → причина → задача актуализации у директора.
   Актуальность, согласование и исполнение показаны раздельно.
4. Главная → назначенный основной визит → политики → заполнение → проверка
   и предварительный PDF → явное завершение → задача ознакомления → результат.
   Открытие отчёта само по себе не закрывает ознакомление.
5. Главная → тот же черновик → тот же вопрос/раздел и сохранённые ответы.
6. Назначенный частичный повторный → только переданные разделы исходного
   аудита → проверка назначенного состава → результат и связь с назначением.
7. Предприятие в ИПУР → поддерживающий/контрольный этап → назначенная проверка.
   Состояние процесса не выводится из одиночного критического «Нет».
8. ПБО → результат → основание → связанный план/действие → состояние исполнения.
   Согласованный план и заявленное исполнение не выдаются за устранение.
9. Аналитика → раздел/частое замечание/история → конкретный визит и ответы.
   Частичный и полный визиты не смешиваются в одной линии без обозначения состава.
10. Перезагрузка → все изменения локального сценария восстановлены;
    сброс X3 затрагивает только его ключ.

## Предметная модель и контракт

`workspace.version = 1` внутри прежнего состояния X3.
Объекты: `sites`, `assignments`, `plans`, `planVersions`, `actions`, `tasks`,
`programItems`, `processes`, `events`, `settings`. Существующие `visits` остаются
частью того же сохранённого состояния.

Все сущности имеют стабильные ID. Ссылки используют ID, а не название ПБО.
`siteId`, `taskId`, `assignmentId`, `planId`, `versionId`, `actionId`, `visitId`
связывают работу и основания. Каждая изменяемая сущность содержит `revision`.
Историческая версия ПД после отправки не меняется задним числом.

Данные читаются через собственный адаптер `workspace-repository.js`:
`load()`, `query(kind, filter)`, `execute(command)`; интерфейс асинхронный.
Команда содержит `id`, `type`, `entityId`, `expectedRevision`, `payload`.
Повтор одной команды не дублирует события. Ошибка/конфликт не показываются
как успешное сохранение. `workspace-domain.js` валидирует переходы;
`workspace-ui.js` отвечает за экраны и связывается с текущим аудитом через мост.

Будущий сервер должен проверять исполнителя/права, revision и допустимость
перехода самостоятельно. Локальные проверки фронта — демонстрационная логика,
не защита доступа. Адаптер не означает, что интеграция уже работает.

## Состояния и права

- ПД: `draft → submitted → approved` либо `returned`; повторная отправка создаёт
  новую неизменяемую версию. КпП может решать только по отправленной текущей версии.
- Задача: `open / waiting / completed`. Решение по ПД закрывает соответствующую
  задачу; ознакомление требует отдельного действия пользователя.
- Действие: `open / in_progress / reported_done / verified / rework`.
  `reported_done` означает заявление исполнителя; `verified` требует отдельного
  подтверждающего. Его роль для ПУСК документами не определена полностью.
- Актуальность ПД — отдельное измерение, вычисляемое из настройки примера,
  даты и наличия активных действий. Демонстрационный порог не называется
  производственной нормой. Неизвестные поля не превращаются в нули.
- ИПУР: `support / control / released`. Данные стадии и перехода принадлежат
  процессу; назначенный успешный этап может переводить пример к следующему,
  обычный визит не снимает ИПУР.

КпП не редактирует план вместо директора и не подтверждает любое действие
автоматически. Для показа передачи работы существует отдельная панель
**«Демонстрация процесса»**: поступление версии от директора, отметка исполнителя,
ответ проверяющего, событие процесса. Каждая такая операция явно подписывает
демонстрационного участника и остаётся в истории. Это не меню реальных прав КпП.

## Демонстрационные данные и спорные правила

Данные примера отделены маркером происхождения от ранее введённых визитов.
На первом запуске добавляются один раз, при миграции существующие ответы не
переписываются. Варианты сценария: ПД ожидает согласования; возвращённая версия;
согласованный план с незавершённым действием; назначенный частичный повторный;
ПБО на поддерживающем этапе ИПУР; ПБО без результатов.

Демонстрационный список ПБО использует существующие ID. Неизвестные реальные
ФИО не придумываются: участники именуются ролями примера.
Фиксированная дата примера — 13.10.2026; сроки подписаны как данные примера.

Полные реальные вопросы есть только для аудита безопасности пищи. Их 48,
файл не меняется. Назначенный частичный повторный использует подмножество
тех же ID/разделов. Поддерживающий/контрольный сценарий при отсутствии настоящего
опросника показывает существующий аудит как демонстрационный состав этапа;
это явно написано до старта и в отчёте. Другие чек-листы можно видеть в программе,
но они не получают вымышленных вопросов или ложной возможности прохождения.

Существующая формула доли «Да» сохраняется как демо. Для частичного визита
знаменатель — назначенный состав; отчёт явно показывает его. «Неактуально»,
порог/веса, фальсификация по типам и точный зачёт цикла требуют отдельного
производственного контракта. План примера считает назначенные обязательства,
а не объявляет число завершённых форм выполнением реальной программы.

Демонстрационный возврат ПД требует объяснения, подтверждение исполнения —
пояснения/доказательства. Эти условия подписаны как сценарий для согласования
с бизнесом и не заявляются требованиями действующей системы.

## Аналитика и визуальные состояния

Матрица разделов имеет горизонтальную прокрутку внутри блока и фиксированные
названия ПБО. Нельзя прокручивать всю страницу по горизонтали. История даёт
выбор ПБО, дату/значение над графиком, альтернативный список/таблицу и кнопки.
Сводки задач/ПД ведут к исходным записям, показывают количество и область данных.
Критические основания видны отдельно от процента. Цвет всегда сопровождается текстом.

Отдельные состояния: loading, empty, unavailable, forbidden, error, conflict.
Мобильные основные действия не меньше 44×44; фокус панелей восстанавливается;
жесты не являются единственным способом навигации.

## Приёмка

Все десять сценариев должны пройти в браузере. Проверяются 320/390 и desktop,
данные до/после перезагрузки, повтор команды, устаревшая версия, возврат контекста,
повреждённые данные, ошибка записи и сброс только X3. 18 существующих тестов
должны продолжить проходить. Источник X1 совпадает с базовым SHA-256,
вопросы X3 совпадают с X2. Перед новой публикацией нужен отдельный запрос пользователя.

## Отложено

Боевой backend/API, авторизация/SSO, серверные права, реальный портфель и назначение,
почтовые уведомления, настоящий многопользовательский аудит, производственные
формулы, полные опросники остальных типов и полноценный offline-first.
Эти пункты не объявляются реализованными готовым фронтенд-прототипом.
