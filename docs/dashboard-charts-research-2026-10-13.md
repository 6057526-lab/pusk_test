# Графики для Dashboard ПУСК: исследование и проверка пригодности

13 октября 2026. Аудитория подтверждена пользователем: КпП, несколько предприятий.
Это кабинетное исследование официальных продуктов, рекомендаций по визуализации
и фактических данных X3. Интервью и пользовательских экспериментов не проводилось.
Ни одна диаграмма пока не прошла проверку пользы с реальными КпП. Ниже — аргументированный
отбор, определения, риски и задания для такой проверки, а не утверждение доказанного ROI.
Графики не внедрены в приложение в рамках этого исследования.

## Рекомендация

Начать с **«Результаты по разделам»**: на компьютере матрица **ПБО × раздел**, на телефоне
полосы для выбранного предприятия. Это две формы одного показателя, а не два независимых
виджета на главной. Рядом обязательно показывать критические «Нет», дату и полноту данных.

Второй кандидат — **частые замечания в последних аудитах предприятий**: короткие
горизонтальные столбцы по вопросам, с числом ПБО и основанием отбора. Третий —
**история одного ПБО** с точками по датам сопоставимых завершённых визитов, в деталях
предприятия. Для каждого нужны достаточные записи; недостаток данных не заменять
вымышленными цифрами. План/просрочки/устранение/IPUR — полезный следующий слой после
подключения соответствующих источников и определения бизнес-правил.

На мобильной главной оставить один аналитический блок после ближайших действий.
У КпП сначала задача выбрать предприятие и следующий шаг, затем исследовать причины.
Большой каталог графиков вынести в «Аналитику». Это рекомендация, требующая проверки.

## Что подтверждают источники

- [Mitti: метрики и атрибуты](https://help.mitti.com/005753) описывает отдельные
  показатели проверок, действий и расписаний и разрезы по объектам, вопросам, срокам
  и исполнителям. [Примеры аналитики](https://help.mitti.com/005101) включают линии
  проведённых проверок/результатов и таблицы отмеченных ответов/расписаний.
  Вывод для ПУСК: количество визитов, качество ответа и устранение — разные показатели.
- [Crunchtime, обновление сентября 2026](https://www.crunchtime.com/blog/whats-new-in-the-crunchtime-suite-september-2026)
  показывает качество исполнения рядом с завершением задач, отдельно рассматривает
  результаты проверок во времени. Это поддерживает раздельные представления плана
  и качества; производственные шкалы ПУСК из продукта не следуют.
- [FoodDocs: продуктовые возможности](https://www.fooddocs.com/food-safety-solutions)
  описывает обзор объектов, тепловые карты, недельные графики и таблицы с детализацией.
  Это свидетельство применения форматов, не доказательство их эффективности для КпП.
- [Government Analysis Function: charts](https://analysisfunction.civilservice.gov.uk/policy-store/data-visualisation-charts/)
  связывает форму с задачей: сравнение категорий — столбцы, изменение во времени —
  линии. Длинные подписи удобнее на горизонтальных столбцах; числовая ось столбцов
  начинается с нуля. Двойные оси могут создавать неверное впечатление связи величин.
- [ONS: pie and doughnut charts](https://service-manual.ons.gov.uk/data-visualisation/chart-types/pie-and-doughnut-charts)
  ограничивает круговые диаграммы составом одного целого: неполные или пересекающиеся
  категории не подходят. Сравнивать несколько распределений кругами неудобно.
- [Saket, Endert, Demiralp: Task-Based Effectiveness of Basic Visualizations](https://arxiv.org/abs/1709.08546)
  сравнивает пять типов визуализации на разных задачах и наборах данных. Эффективность
  зависит от задачи. Работа не тестирует ПУСК, КпП или именно наш будущий мобильный экран.

## Проверка исходных данных

Сейчас `enterprise-audit` хранит ПБО, дату визита, признак завершения, ответы на
48 фиксированных вопросов, критичность, комментарии/фото и факт фальсификации.
Данные локальные. Пример визита помечен `example` и исключается из аналитики.
Пользователь утвердил демонстрационную долю «Да», с безусловным неудовлетворительным
результатом при критическом «Нет» или фальсификации. Это не утверждённый производственный балл.

Нет плановых назначений/дедлайнов, истории статусов исправления, реестра IPUR,
состава реальной зоны КпП, геокоординат, выручки, длительности активной работы
или производственной версии шкалы. `version:1` в сохранении — версия состояния
приложения, не версия чек-листа. `completedAt` — момент завершения, не время начала.

Для портфельного сравнения брать **один последний релевантный завершённый визит
каждого ПБО в периоде**. Иначе предприятие с частыми повторными проверками получит
больше веса. Дату каждого результата показывать: записи разных дат не образуют
синхронный срез. Черновики, отсутствие данных и демонстрационные примеры не превращать
в нули. Не смешивать разные типы/версии аудита. Локальный список ПБО не гарантирует
охват всей зоны; подпись о покрытии обязательна.

## Проверка каждого кандидата

Оценки ниже качественные. Не создаём искусственный «балл валидности» или рейтинг
из произвольных весов. Для каждого формата проверены задача, действие, единица
наблюдения, расчёт, источник, читаемость и риск неверного вывода.

### 1. Матрица «ПБО × раздел» — рекомендовать для портфеля

**Вопрос / действие:** где и в каком разделе хуже ответы; открыть ПБО и конкретные
вопросы. **Расчёт:** «Да» / все вопросы раздела в последнем завершённом релевантном
аудите, строго по текущему демо-правилу; рядом «Нет», критические «Нет» и «Неактуально».
**Источник:** вопросы и результаты есть. Для реального сравнения нужны версия
опросника, правило шкалы и покрытие зоны. **Представление:** ячейка с числом и датой,
нейтральная последовательная насыщенность цвета; критический ответ — отдельный
подписанный знак. Не придумывать красные пороги балла. На телефоне выбрать ПБО,
показать его разделы; широкая матрица — desktop.

**Риск:** высокий процент выглядит безопасным при критическом «Нет»; старый
результат выглядит актуальным; пустая ячейка выглядит нулём.
**Проверка:** показать 96% + критическое «Нет» и ПБО без визита. КпП должен открыть
критическое основание и сказать, что второе ПБО оценить нельзя. Ошибка отменяет дизайн.
**Вердикт:** сильный кандидат; возможна реализация на локальных результатах, без
обещания текущего состояния бизнеса. При одном ПБО полезнее полосы, чем матрица.

### 2. Горизонтальные полосы разделов — рекомендовать для выбранного ПБО

**Вопрос / действие:** какие разделы конкретного визита проверить подробнее.
**Расчёт / данные:** те же, что у матрицы. **Форма:** шесть полос 0–100%, рядом
«Да: n/N», дата, критический маркер; порядок исходных разделов сохраняется.
**Риск:** разные размеры разделов и доля «Неактуально» скрыты в проценте; длинные
подписи обрезаются. **Проверка:** попросить сравнить 1/2 и 10/20 и найти критический
вопрос. Пользователь должен понимать одинаковую долю и разное основание расчёта.
**Вердикт:** лучший первый мобильный формат; не дублировать им матрицу одновременно.

### 3. История результатов ПБО — рекомендовать в деталях, при наличии истории

**Вопрос / действие:** как изменились ответы между визитами; открыть даты с ухудшением.
**Расчёт:** одна точка = завершённый аудит одного ПБО; Y = демонстрационная доля «Да»,
X = дата визита с реальными интервалами. Под графиком отдельно число критических «Нет»
и фальсификация для каждой даты. Только сопоставимый аудит и шкала.
**Источник:** локальные даты/ответы есть; производственная версия/шкала не подтверждены.
**Форма:** точки, прямые соединения только внутри сопоставимой серии, без сглаживания.
Один визит — одна точка и «Для сравнения нужен ещё визит»; два визита показывают изменение,
но не доказывают устойчивый тренд или эффект работы КпП. Временные разрывы/смену методики
обозначать явно; неизвестные значения не соединять и не заменять нулями.
**Риск:** серия по разным предприятиям выдаётся за улучшение; высокий балл маскирует
критичность. **Проверка:** одинаковый балл при новом критическом ответе, неравные интервалы
дат, смена шкалы. **Вердикт:** полезен в деталях; пока не линия «качество всей зоны».

### 4. Частые замечания по вопросам — рекомендовать вторым этапом

**Вопрос / действие:** какую общую практику проверить/разобрать в нескольких ПБО.
**Расчёт:** по одному последнему релевантному аудиту ПБО; для каждого вопроса число
разных ПБО с «Нет». Показывать n/N обследованных применимых ПБО, «Частично Да» отдельно;
при исключении «Неактуально» из основания явно писать это. Это новый аналитический
показатель, не изменение утверждённого демо-балла. Его определение согласовать.
**Источник:** ответы/ID доступны; устойчивость вопроса и версии нужны для общего процесса.
**Форма:** до пяти горизонтальных столбцов, числа и раскрытие всех вопросов. Критические
ответы доступны отдельно, даже когда не попали в частотный топ.
**Риск:** большая частота путается с тяжестью; 1/1 сравнивается с 3/20 как надёжный рейтинг;
повторные визиты одного ПБО раздувают частоту.
**Проверка:** один критический случай против многих некритических; одно ПБО с десятью
повторными визитами; разные N. **Вердикт:** релевантен, но при малом охвате лучше список
«Зафиксированные замечания». Не называть частоту «повторяемостью после исправления».

### 5. План/факт по ПБО или типу визита — рекомендовать после данных плана

**Вопрос / действие:** где отставание; открыть просроченное назначение.
**Единица:** уникальное плановое назначение, а не любая заполненная форма.
**Расчёт:** зачтено / запланировано; отдельные числа просроченных незачтённых и будущих
назначений. Отмена/перенос/IPUR/новые ПБО требуют правил. **Источник:** сейчас отсутствует.
**Форма:** горизонтальная полоса плана с числом n/N; просрочки отдельной подписью.
Сегменты возможны только при полной, взаимоисключающей классификации назначений.
**Риск:** 0/0 превращается в 0%; любой повторный визит «выполняет» план; зелёный план
воспринимается как устранение проблем. **Проверка:** выполненный план с критическим «Нет»,
отменённое назначение, незапланированный повторный визит, отсутствие плана.
**Вердикт:** высокая бизнес-ценность, сейчас только «Данные не подключены».

### 6. Просроченные действия по возрасту — рекомендовать после учёта исправлений

**Вопрос / действие:** что просрочено дольше и кому передать на проверку.
**Единица:** действие с согласованным сроком и подтверждением закрытия.
**Расчёт:** возраст просрочки = текущая дата минус срок незакрытого действия;
закрытие исполнителем и проверенное закрытие различать по утверждённому процессу.
**Форма:** столбцы по интервалам дней плюс число критических; интервалы — настройка
представления, не выдуманный SLA. На телефоне список действий часто полезнее графика.
**Источник:** нет. **Риск:** нет срока = «не просрочено»; визит завершён = проблема устранена;
давние открытые действия исчезают при фильтре периода обнаружения.
**Проверка:** действие из прошлого периода, без срока, выполненное без подтверждения.
**Вердикт:** условно полезен; прежде очередь с владельцем и сроком, затем диаграмма.

### 7. Обнаружено / подтверждённо устранено / остаток — отложить

**Вопрос / действие:** успевает ли команда устранять замечания; пересмотреть нагрузку.
**Расчёт:** открытый остаток на конец периода = начальный остаток + новые + переоткрытые
− подтверждённо закрытые − другие согласованные выбытия. Нельзя вычитать любые найденные
ответы из любых завершённых визитов. **Форма:** отдельные маленькие графики потока и
остатка; одинаковые периоды, явные единицы, без двойной оси.
**Источник:** нет журнала событий и начального остатка.
**Риск:** больше выявлено = «стало хуже», хотя проверок стало больше; частичные данные
выдают ложный спад остатка. **Проверка:** изменение числа проверок, переоткрытие, поздняя
регистрация. **Вердикт:** для руководителя процесса после достоверного учёта событий.

### 8. IPUR: сроки пребывания — условно рекомендовать как временную шкалу

**Вопрос / действие:** какие ПБО долго в процессе и какой следующий шаг.
**Единица:** отдельный эпизод IPUR с постановкой/выходом. **Форма:** полоса времени
по каждому ПБО; незавершённый эпизод до даты среза, следующий визит подписан. При нескольких
ПБО достаточно таблицы с датами и действием. **Источник:** в X3 отсутствует.
**Риск:** смешать открытые и закрытые эпизоды, сумму дней назвать эффективностью,
среднее только по вышедшим ПБО принять за скорость работы со всеми.
**Проверка:** открытый старый эпизод и быстро закрытый новый, повторная постановка.
**Вердикт:** сначала таблица IPUR; диаграмма при полезной истории, без автоматических порогов.

### 9. Календарь визитов — условно рекомендовать для организации работы

**Вопрос / действие:** что назначено на ближайшие дни; открыть/перенести назначение.
**Источник:** даты проведённых визитов есть, плановых назначений нет.
**Форма:** мобильная повестка на неделю; на desktop календарь. Тепловая карта
проведённых визитов отражает лишь активность. **Риск:** интенсивность проверок принимается
за выполнение программы, два визита за день путаются с двумя обследованными ПБО.
**Проверка:** два визита одного ПБО и день без плановых назначений.
**Вердикт:** повестка с плановыми данными полезнее «календаря активности» на главной.

### 10. Scatterplot «план × результат» — не для первой главной КпП

**Вопрос:** сопоставить процесс и результаты большого портфеля. X = выполнение плана,
Y = результат сопоставимого аудита, точка = ПБО. **Источник:** план отсутствует.
**Риск:** квадранты выдумывают пороги; высокий общий процент скрывает критический ответ;
разные даты/охват искажены; положение не объясняет действие. Для нескольких ПБО таблица
проще. **Проверка:** точка с 100% плана, высоким баллом и критическим «Нет».
**Вердикт:** возможен в аналитике руководителя после данных; размер пузыря не добавлять
без отдельной обоснованной величины. Корреляция не доказывает причинность.

### 11. Donut / круг «здоровье ПБО» — отклонить в предложенном виде

**Почему:** IPUR, черновики и замечания могут пересекаться, а ПБО без данных не являются
благополучными. Сектора не образуют честное целое. Даже корректный круг «завершено/в работе»
считает визиты, а не выполнение плана или качество предприятий.
**Проверка:** ПБО одновременно с черновиком и IPUR; ПБО без визита. Одно предприятие не
должно искусственно попадать в два сектора одного целого.
**Вердикт:** независимые счётчики и списки. Круг допустим для отдельного полного
взаимоисключающего состава, если есть конкретная задача, но не входит в первый набор.

### 12. Radar / спидометр общего балла — отклонить для ежедневного обзора

**Почему:** радар усложняет чтение длинных названий разделов и сравнение отдельных
значений; площадь зависит от расположения осей. Спидометр занимает место, но
по одному числу не объясняет основание и следующий шаг. Общий высокий балл скрывает
критический ответ; производственные пороги не согласованы.
**Проверка:** поменять порядок осей при тех же ответах; 96% с критическим «Нет».
**Вердикт:** полосы с n/N и критическими маркерами; общий балл только с явным смыслом.

Дополнительно: не брать карту без координат и задачи маршрутизации, 3D/анимацию без
аналитической пользы, двухосный график «визиты + качество», автоматический Pareto 80/20
без корректной единицы событий и бизнес-основания. Число визитов в месяц возможно
показать, но это активность, не эффективность или выполнение программы.

## Как реально валидировать

1. С владельцем процесса пройти данные одного ПБО: назначение → визит → ответ → действие
   → подтверждение. Зафиксировать определения показателей/дат и допустимые сравнения.
2. С 5–6 КпП проверить матрицу/полосы, частые замечания и историю против простой таблицы
   на одинаковых сценариях; чередовать порядок. Дополнительно владелец процесса проверяет
   содержательные ошибки. Это план исследования; участники ещё не привлечены.
3. Для каждого графика дать задачу выбрать ПБО/вопрос, объяснить основание и открыть
   конкретную запись. Записать правильность решения, время, ошибки чтения и уверенность.
4. Обязательно включить критический «Нет» при высоком балле, отсутствие визита,
   разную дату результатов, малый N, «Неактуально», старую шкалу и несколько повторных
   проверок одного предприятия. Специальные случаи кандидатов описаны выше.
5. Предлагаемый критерий допуска: отсутствие опасного вывода «высокий процент = безопасно»
   или «нет данных = всё хорошо»; верное действие и понятное основание; преимущество
   над таблицей по времени/ошибкам либо объяснимое преимущество для конкретной задачи.
   Числовые пороги теста согласовать до исследования. Малый тест не доказывает ROI.

Всплывающая подсказка не должна быть единственным носителем значений. Клик/касание и
клавиатура открывают записи; есть доступная таблица. На 320–390 px подписи читаются,
цвет дублируется числом/текстом. Заголовок сообщает показатель, область и период.
Переход к вопросу/визиту сохраняет фильтры и возврат; экспорт содержит те же ограничения.

## Очередность внедрения

**Сейчас после выбора:** матрица/полосы результатов, только реальные сохранённые
завершения и явно подписанный демо-расчёт. Не показывать фальшивую динамику при одном визите.
**Затем:** частые замечания и история, когда записей достаточно для полезного сравнения.
**После источников бизнеса:** план/факт, действия и IPUR. Не достраивать эти графики
из количества визитов и критических ответов.

Иллюстрации в отдельном `output/dashboard-charts-2026-10-13/review.html` используют
синтетические ПБО A/B/C и условные разделы, исключительно для оценки формы. Это не
новые вопросы аудитa и не данные ПУСК; они не сохраняются в приложении.

Пользователь отметил исчезновение матрицы, мелкую мобильную форму и потребность

### Несколько предприятий: два уровня анализа

1. **Обзор всех ПБО.** Матрица последних результатов, даты и охват. Название ПБО
   закреплено слева при прокрутке шести разделов. Ячейка ведёт к выбранным ПБО
   и разделу; пустые результаты подписаны словами и не получают 0%.
2. **Разделы одного ПБО.** Полосы со шкалой 0–100%, долей и количеством «Да»;
   выбранный раздел показывает основание. Между предприятиями можно переключаться.
3. **Замечания портфеля.** Количество разных ПБО с «Нет» по одному последнему
   визиту. Выбор вопроса раскрывает предприятия с этим ответом. Необследованные
   ПБО не входят в знаменатель. Критичность остаётся отдельным признаком.
4. **История.** По умолчанию отдельные карточки всех ПБО, с одинаковыми осями
   0–100% и периодом 01.09–13.10.2026. После выбора предприятия — подробный
   график: свайп прокручивает время, касание выбирает наблюдение, дата и значение
   стоят над графиком. Нет среднего балла портфеля или общей соединённой линии.

Для небольшого портфеля отдельные истории позволяют не смешивать даты и не
скрывать критический ответ за общей средней. Это проектное решение, которое
нужно сравнить с таблицей на задачах КпП. При десятках ПБО понадобятся поиск,
фильтры и сортировка по задаче; в учебной галерее из трёх ПБО они не имитируются.

### Что изменено в галерее

Явный переключатель «С данными / Нет данных» постоянно показывает выбранный
режим. При выборе другого формата открывается пример с данными. ПБО C без визита
остаётся предусмотренным учебным набором состоянием, независимо от режима.
Матрица, разделы, замечания и истории теперь используют один согласованный
синтетический набор: A — 42/48 «Да» (87,5%), B — 47/48 (97,9%), у каждого один
критический «Нет» в разделе F; C — без визита. У A три «Нет» и три «Частично Да»;
у B один «Нет». «План / факт» остаётся отдельным будущим примером.

Галерея не читает и не записывает localStorage, не открывает реальные ответы и
не меняет X3. Детализация демонстрирует будущий переход; интеграция с приложением
остаётся следующим решением. Исходные вопросы и производственные формулы не менялись.

### Выполненная проверка галереи

В браузере проверены все пять форматов на ширинах 320 и 390 px: горизонтального
переполнения страницы нет. Матрица прокручивается внутри карточки; имя ПБО остаётся
у её левого края. На обычной ширине desktop все шесть разделов помещаются без

сохранение фокуса на выбранной дате и возвращение из режима «Нет данных».
В журнале браузера ошибок нет; JavaScript проходит проверку синтаксиса.
