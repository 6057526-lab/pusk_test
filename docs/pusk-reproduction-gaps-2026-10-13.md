# Что нужно для воспроизведения ПУСК

Дата: 13 октября 2026 года. Основание: просьба пользователя установить конкретные пробелы, найти доступные источники и выделить вопросы, ответы на которые уже есть.

База позволяет описать основные пользовательские маршруты и начать проектирование системы. Для точного воспроизведения не хватает технической конфигурации ELMA365 и однозначных правил расчёта, доступа и переходов процессов. Часть сведений уже есть в переданном пакете; другие можно извлечь из конфигурации и внутренних постановок. Открытая документация объясняет механизмы платформы, но не определяет правила конкретного внедрения ПУСК.

## Два способа воспроизведения

**Перенос на ELMA365.** Нужны версия и поставка платформы, экспорт компонентов ПУСК, зависимости, настройки окружения, справочники и данные для проверки. В этом случае серверная логика может находиться в схемах бизнес-процессов, скриптах, приложениях и модулях ELMA365. Искать только отдельный репозиторий «backend» недостаточно.

**Самостоятельная система с фронтом и бэком.** Из материалов нужно восстановить поведение, затем выбрать модель хранения, API, авторизацию, выполнение задач и расписаний. Технологии новой системы можно выбрать самостоятельно; исходники всей платформы ELMA365 для этого не обязательны. Правила доступа, результаты расчётов и последствия действий должны иметь подтверждённую спецификацию.

Выбор способа пока не сделан. Этот разбор не меняет [архитектуру прототипов](prototype-architecture.md) и не утверждает архитектуру будущего продукта.

## Что удалось найти в открытых источниках

Официальная документация ELMA365 даёт конкретный путь извлечения конфигурации:

1. **Экспорт решения в `.e365`.** Экспорт анализирует внешние зависимости; часть связей требует переноса зависимых решений. Если ПУСК оформлен как экспортируемое решение и есть соответствующий доступ, такой пакет может существенно сократить восстановление вручную. Состав ПУСК и полноту переноса нужно проверить отдельно; экспорт конфигурации не следует считать готовой копией рабочих данных и окружения. [Документация экспорта](https://elma365.com/ru/help/platform/export-solution-file.html).
2. **Схема приложения через API.** Описан метод `GET /pub/v1/scheme/namespaces/{namespace}/apps/{code}`. Он может помочь получить фактическую структуру приложений вместо предположений по экрану. [Описание метода](https://api.elma365.com/ru/public-api/reference/scheme/applicationentityget/).
3. **Схема шаблона процесса через API.** Описан метод `GET /pub/v1/scheme/namespaces/{namespace}/processes/{code}`. Полноту схемы и наличие всей пользовательской логики в ответе нужно проверить на соответствующей версии. [Описание метода](https://api.elma365.com/ru/public-api/reference/scheme/processget/).
4. **Доступ к API не анонимный.** Запросы выполняются с токеном пользователя и соответствующими правами. Доступность этих методов в конкретной версии ПУСК ещё не проверена. [Авторизация API](https://api.elma365.com/ru/public-api/guides/WebAPIAuthorization/).
5. **Пользовательская серверная логика может быть в модуле.** ELMA позволяет создавать методы API, процессы, обработчики событий и сервисы. При инвентаризации ПУСК нужно учитывать эти компоненты. [Создание модуля](https://elma365.com/ru/help/platform/create-extention.html).

В поиске по официальным сайтам ELMA365 и «Вкусно — и точка» по сочетанию названий продукта и компании спецификацию внедрения ПУСК найти не удалось. Это ограниченный результат поиска, а не доказательство отсутствия любых публичных материалов. Производственные веса ответов, права и реестр ПБО из общей документации платформы получить нельзя.

## Вопросы которые пока нельзя закрыть однозначно

1. **Как считается результат?** Среднее процентов разделов и процент по всем вопросам дают разные итоги. Пример: в первом разделе 1 «Да» из 1, во втором 1 из 3. По всем вопросам — 50%, среднее разделов — около 66,7%. В импортированном прототипе `js/state.js`, функция `calcVisit`, используется среднее округлённых процентов разделов; в нашем X3 — демонстрационная доля «Да». Ни одну из этих реализаций нельзя считать производственной формулой без сверки с весами и расчётом ELMA.
2. **Где допустима фальсификация?** Текст проекта относит её к визиту «по людям», а путь аудита и согласованное демо показывают окно шире. Требуется правило по типам чек-листов.
3. **Что означает возраст ПБО?** Старое правило выделяет «Бизнес-планирование» и два месяца; замечания 12.10 описывают 60 дней/IPUR в подсказке. Календарные месяцы и 60 дней различаются. Нужны тип визита, точная граница и правило обработки даты.
4. **Каковы целевые права на ПД?** Документы 05–07.10 показывают 403 для КпП, снимок 08.10 — доступную таблицу. У директора наблюдались чужие ПД. Требуется отделить нынешнее поведение от согласованной видимости.
5. **Что считается актуальным ПД?** Параметр срока найден, но базовая дата, включительность границы, статусы активных действий и подтверждение исполнения не определены полностью.
6. **Что происходит при архивации и изменении периода?** Старый документ запрещает менять даты опубликованного чек-листа, более новый фиксирует редактируемую форму. Доступность редактирования не определяет последствия для расчётов и запущенных визитов. Нужны точные правила сохранения истории.
7. **Как считается цикл после изменений?** Сверка 08.10 прямо отмечает, что формула после PCW-4112 не выводится из видимых ячеек. Сведения о старом исправлении PCW-1632 не закрывают этот вопрос.
8. **Кто получает письма?** Таблица уведомлений прямо отмечает расхождение: в PCW-1901 при снятии с IPUR есть МпП, в описании БП его нет. Нужна актуальная настройка и целевая матрица.
9. **Какие правила действуют для верификаций?** Повторы, «Регулирование визитов», сроки и прямой доступ КпП остаются открытыми; приблизительные 60 чек-листов в год не являются точной периодичностью.

Основания: [разбор противоречий роли КпП](kpp-role-analysis-2026-10-13.md), [сверка 08.10](../reference/pusk-context-2026-10-13/contents/pusk/runs/proto_compare_20261008/СРАВНЕНИЕ-стенд-прототип-2026-10-08.md), [уведомления](../reference/pusk-context-2026-10-13/contents/pusk/домен/уведомления.md), §10 описания проекта.

## Порядок дальнейшей разведки

1. Получить отсутствующий снимок БП и журнал Трекера из основного репозитория. Они позволяют уточнить правила без новых проходов системы.
2. Получить паспорт окружения и экспорт конфигурации ПУСК с зависимостями либо доступ к чтению соответствующих схем. Отдельно получить актуальные справочники и параметры.
3. Зафиксировать модель данных, расчёт результата, права и переходы процессов. Для каждого спорного правила хранить вопрос, источник, дату, ответ и эталон проверки.
4. Проверить обезличенные примеры: успешный визит, критический провал, «Частично Да», «Неактуально», повторный, IPUR, согласование/отклонение ПД, смена КпП и смена цикла. Пустой справочник или недоступная тестовая запись не подтверждают отсутствие функции.
5. Передать владельцам только оставшиеся вопросы о целевом поведении. Технологические решения самостоятельной системы сформулировать отдельно от правил бизнеса.

Первый полезный комплект: **полные схемы БП + конфигурация/схемы приложений + справочники с весами и регламентами + эталонные результаты + актуальная матрица прав**. Именно он превратит подробный контекст в основу воспроизводимой реализации.
